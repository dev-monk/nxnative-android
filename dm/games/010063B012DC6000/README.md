# SHIN MEGAMI TENSEI Ⅴ (`010063B012DC6000`)

Base game 1.0.0 (v0), SDK 9.3.1 (its own `sdk` build). ATLUS, Unreal Engine 4.23 (`++UE4+Release-4.23`): one pak with the shaders inline in the cooked packages, NVN, CRIWARE (ADX2 sound, Sofdec movies). Modules `main`, `subsdk0` (NintendoSDK_movie, which `main` imports from) and `sdk`. 60 fps (30 on the Switch) by the host's writes of Unreal's frame limits.

Status: plays on the iPhone 18 Pro Max (user: gameplay fine; IPA about 14.5 GB). On the Mac, a new game through the opening and the character naming to the first classroom (Jouin High School 2F) runs at 60 fps (frame time p50 16.7 ms) with the buffer-image fix of [PR #263](https://github.com/seedds/nxnative/pull/263); without it the host stops about 60 s into a new game. Seven `[RED]` lines remain, from two compute shaders the translator does not take ([Rendering](#rendering)). The iPhone build predates the image-atomic admission (PR #178).

## Frame rate

- **Current:** 60 fps (30 on the Switch). The game caps Unreal at 30 twice: its code sets `t.MaxFPS` 30 at run time (its config has no `t.MaxFPS` or `FrameRateLimit`; frame smoothing is off in `Engine/Config/Switch/SwitchEngine.ini`), and the engine's Switch device profile sets `rhi.syncinterval=2` (`BaseSwitchDeviceProfiles.ini`), the present interval 2 it asks for while `r.VSync=1` locks presents to vsync. The host writes 60 and 1 into the two console variables whenever the game sets them back (registered at `main+0xc7ba64` and `main+0xbd00ac`; the TAutoConsoleVariable holds at +0x10 the pointer to its value, the game thread's copy then the render thread's, and the host writes both). `rhi.SyncInterval` 1 alone left it at 30.
- On the Mac the route from a new game to the classroom ran at frame time p50 16.7 ms at 60 fps and 33.3 ms at 30, at the game's own speed: the naming keyboard appeared at the same wall time at either rate. Unreal steps the game by the time that really passed.
- On the iPhone the GPU took 8–27 ms a frame at 30 fps, so busy scenes may fall back to 30. `DM_FPS_TARGET=30` (`Documents/env.txt`) or the settings screen's Frame rate keeps the game's own 30 and saves power.

## Memory

- `nninitStartup` (`main+0x1885750`) reserves the engine region with `AllocateAddressRegion`, 62 GB unless `-SwitchVirtualAddressSpaceSize=` (MB up to 4095) gives a size. This build allocates the region only when no size was given (`if (!size) { size = 62 GB; AllocateAddressRegion(&base, 62 GB); }`, `main+0x1885ae4`), so with the option alone the base stayed 0 and the engine's page allocator (`main+0x1872af0`) would have handed out [0, size). The two cuts keep the test for the default and allocate a region of the size given; the lazy initialisation at `main+0x1872a40` has the same test, but `nninitStartup` runs first and sets the size: [Unreal's engine address region and its options](../../../docs/reference/memory.md#unreals-engine-address-region-and-its-options).
- **Current: the allocator is the host's.** Its FMallocBinned3 would take 37 GB of the region (74 pools of 512 MB, pool index = offset >> 29; the alias region's high-water mark reached +38.5 GB of 64 GB at boot). `GCreateMalloc` mallocs 0x1c38 bytes on the first allocation and constructs them (`main+0x1713920` → `main+0x17098b0`), then stores GMalloc (`main+0x6abc8b8`). The constructor call is cut, and the gate takes the store two instructions later: the `adrp` right after the call is PC-relative ([Observation gates where x9–x17 are dead](../../../docs/reference/rewriter.md#observation-gates-where-x9x17-are-dead)). Nothing outside the allocator reads its pool base (`main+0x6a8f568`: every reference is in `main+0x170a0ec` … `+0x170e504`) or calls its methods directly (they are reached only through the vtable `main+0x57e6238`); the one call into its code from outside (`main+0x1872d70` → `+0x170aa50`) builds a bit tree in the caller's own object. UE 4.23's FMalloc has 18 slots, no `TryMalloc` / `TryRealloc` yet: [Unreal's FMallocBinned3 replaced by the host allocator](../../../docs/reference/memory.md#unreals-fmallocbinned3-replaced-by-the-host-allocator).
- **Current: a 4064 MB region** with the node-area and alignment cuts on this SDK 9.3.1 build (the AddressRegionManager constructor `sdk+0xd2230`, `VammManager::AllocateAddressRegion` `sdk+0xd2340`), in Engage's 5 GB block: the region starts 64 MB into the 4.375 GB alias region ([The SDK's address-region node area](../../../docs/reference/memory.md#the-sdks-address-region-node-area)). On the Mac from the opening to the first classroom, at 30 fps: the region mapped up to +1.25 GB (1.0 GB in use), the Unreal heap at 0.75 GB, the sparse virtual pools holding up to 0.44 GB of address space reserved over 755 pools, a 2.9 GB footprint. On the iPhone: a 1.9 GB footprint in play.

## Rendering

- **Resolved: `[RED] MapVirtual: non-contiguous mapping (true sparse) not implemented`, a few hundred times.** Unreal's NVN RHI gives each streaming texture a virtual pool of its own (flags 0x2a1, 128 KB to a few MB, over a thousand by the opening) and maps it 64 KB page by page from some twenty physical pools, the first request often for a level past the pool's start. Pools that small kept the alias, so every request after the first that named another place failed. The profile's `virtual_pools sparse` makes every one sparse: [Small virtual pools made sparse](../../../docs/reference/nvn-objects.md#small-virtual-pools-made-sparse-virtual_pools-sparse). The game finalizes these pools all the time; a sparse texture whose pool is gone keeps its last upload ([Sparse textures bound from their first mapped level](../../../docs/reference/rendering.md#sparse-textures-bound-from-their-first-mapped-level)).
- **Resolved: Unreal's out-of-memory abort at boot** after a 0xffe00000-byte pool request: the RHI sizes a sparse texture's mip tail from `nvnTextureBuilderGetSparseTileLayout`, whose stub left a tiled level count past the texture's levels: [The sparse tile layout of a texture](../../../docs/reference/nvn-objects.md#the-sparse-tile-layout-of-a-texture).
- **Resolved: the whole picture black** in the classroom. The engine writes the classroom's 256x16 colour-grading LUT from the CPU into an ordinary pool after creating it; the LUT held its data in guest memory but read 0 on the host, so the tonemapper's LUT came out 0. Both `tex_flush_upload` and `tex_dirty_upload` are on: [CPU writes with no flush, caught by page protection](../../../docs/reference/nvn-objects.md#cpu-writes-with-no-flush-caught-by-page-protection-tex_dirty_upload).
- **Resolved: the classroom's walls in bright and dark patches.** Its 1024×1024 and 1024×512 DXT5 lightmaps are sparse textures with no packaged layout, read with the automatic block height (16 GOBs) and scrambled in 4-texel columns. With 8 GOBs the game's level 1 is its level 0 halved (mean difference of the blocks' first colour 23, against 139 or more with 16 in either level): [Block height of sparse textures with 8- or 16-byte blocks](../../../docs/reference/rendering.md#block-height-of-sparse-textures-with-8--or-16-byte-blocks).
- **Resolved: the naming cutscene green, then white** (every lit surface green from the cutscene's first frame, then the picture washed out). Unreal 4.23 captures its sky light again as the cutscene loads: it clears two 128×128 scratch cubes, every face and level, to (0, 10000, 0, 0) (`ClearScratchCubemaps`' "noticeable value"), draws each face of the source cube into them and projects the result to spherical harmonics, the sky irradiance every lit pixel reads (`SkyIrradianceEnvironmentMap` in the View uniform buffer). Face 0 kept the clear's green: its draw ran under the 1×1 scissor of the last level cleared, though the game had set 128×128 before it. The prewarm list is empty, so pipelines are built on demand, and the precompile look-ahead lost the scissor, the bug first found on OCTOPATH TRAVELER II: [The precompile look-ahead restores the scissor](../../../docs/reference/shaders.md#the-precompile-look-ahead-restores-the-scissor). Comparing each pass's first draw's scissor with the game's last `SetScissor` over 50 frames of the cutscene's load: 3 draws off before the fix, 0 after.
- **Current: 7 `[RED]` lines, two of Unreal's global compute shaders not translated** (`4f731ba19a5f2877` and `c073d1efaba9ac70`, from `GlobalShaderCache-GLSL_SWITCH.bin`). Their atomics on a 4-byte buffer image use the value they return: `c073d1efaba9ac70` adds to a counter and exchanges the result into a table of list heads (a linked list), `4f731ba19a5f2877` adds and appends. The translator's bounded Metal atomics take only atomics whose result is discarded ([Bounded MSL 2.3 atomic emulation](../../../docs/reference/shaders.md#bounded-msl-23-atomic-emulation)), so their dispatches are skipped. They matter a little: with the translations of the chain before that change put back on the same host (the same arguments, no bounds checks), the classroom at frame 29,000 has a mean luma of 58.8, against 56.8 to 57.3 without them (58.5 on an older host that still had them): the whole frame a little darker and its colours slightly shifted, hard to see side by side. Likely Unreal's light grid (not confirmed).

## Files and shaders

- Its one pak, `Project/Content/Paks/pakchunk0-Switch.pak` (the profile's `romfs_marker`): 8.8 GB, version 8, Zlib blocks, the index and the `.uasset` files AES-encrypted. The key comes from a key callback in `main` (`main+0x14180c0`) whose two 16-byte halves are literals 0x1460 bytes apart (`uepak.py` `callback_keys`; it stays in memory, never printed).
- Shaders: 18,558 unique (6,440 vertex, 11,608 pixel, 478 compute, 32 geometry), inline in the cooked packages: the engine's global shaders (`Engine/GlobalShaderCache-GLSL_SWITCH.bin`), the engine's materials and the game's ([Unreal Engine 4.23 shaders inline in an encrypted version 8 pak](../../../docs/reference/shaders.md#unreal-engine-423-shaders-inline-in-an-encrypted-version-8-pak)). The game has no PC version in this repository, so the facts table holds only compute group sizes; every vertex shader is made to link with any pixel shader (`shader_split.py` `separable_pairs`). The `shader_note` is still the provisional profile's: `shader_*` keys are part of every shader's cache key, and the libraries were built with it.

## Found on this game

General changes first needed here; each applies to every game:

- **Legacy version 8 Unreal paks, deleted pak entries skipped, and AES keys from a key callback** (`uepak.py` `LEGACY`, `footer`, `callback_keys`, `pak_key`; `shader_split.py` `ue_legacy_jobs`): [Unreal Engine 4.23 shaders inline in an encrypted version 8 pak](../../../docs/reference/shaders.md#unreal-engine-423-shaders-inline-in-an-encrypted-version-8-pak).
- **UE 4.23's FMalloc layout** (`UE4_23` in `hle_uemalloc.c`, with no `TryMalloc` / `TryRealloc` slots): [Unreal's FMallocBinned3 replaced by the host allocator](../../../docs/reference/memory.md#unreals-fmallocbinned3-replaced-by-the-host-allocator).
- **The profile key `virtual_pools sparse`, and sparse virtual pools with no fixed limit** (`vp` in `pool_t`, `vps_find`; `nvn_sparse_alias` searches the same list): [Small virtual pools made sparse](../../../docs/reference/nvn-objects.md#small-virtual-pools-made-sparse-virtual_pools-sparse).
- **The sparse tile layout queries** (`nvnTextureGetSparseTileLayout`, `nvnTextureBuilderGetSparseTileLayout`, `nvn_tex_sparse_tiles`): [The sparse tile layout of a texture](../../../docs/reference/nvn-objects.md#the-sparse-tile-layout-of-a-texture).
- **A block height of at most 8 GOBs for sparse textures with 8- or 16-byte blocks and no packaged layout** (`nvn_tex.c`, a `t_tex` case): [Block height of sparse textures with 8- or 16-byte blocks](../../../docs/reference/rendering.md#block-height-of-sparse-textures-with-8--or-16-byte-blocks).
- **A sparse texture whose pool the game finalized keeps its last upload** (`tex_t` `sparse`, `vpool_tex`, `t_sparse_life`): [Sparse textures bound from their first mapped level](../../../docs/reference/rendering.md#sparse-textures-bound-from-their-first-mapped-level).
- **Buffer images declared as buffers for image atomics** (`nvn_refl.m`; `dummy_img_tbuf`, `dummy_atom_buf`, `t_imga_tbuf`), in [PR #263](https://github.com/seedds/nxnative/pull/263): without it the image-atomic admission stops the host at `05fe2caae79b6e53`'s first dispatch, about 60 s into a new game.
- **`texraw` reads a packaged texture at the level it is sampled from** (`dm_gfx_texraw`; a sparse texture's first mapped level).
- **The Screen setting on iOS** (`DM_ASPECT` = `fit` | `zoom` | `stretch`, default `fit`; `dm/games/settings.tsv`, `front_ios.m` `dm_game_rect`, `DmGamepad.m`): Fit keeps the 16:9 picture with black bars; Zoom fills the screen and cuts off what does not fit (the top and bottom on an iPhone); Stretch fills it and changes the picture's shape. Touches on the game's screen map to the same rectangle ([Settings](../../../docs/settings.md#screen)).

## Open

- The two compute shaders in [Rendering](#rendering): they need atomics whose result is used in the translator's Metal path, with a defined result for a coordinate out of bounds. A change of the translation chain, so every game's shaders are rebuilt.
- No prewarm list yet: [`pso_manifest.tsv`](pso_manifest.tsv) is the provisional profile's, empty until recorded on the Mac, so new scenes compile their pipelines on first use.
- `CRASH sig=10` at `main+0x3617108` (a read at 0xd0000003f; backtrace `main+0x31840d4` ← `main+0x30241d8` ← `main+0xcbba70`), once on the Mac 5.8 s into the boot, in an early bring-up run that still had Unreal's own allocator and the 62 GB region (the alias region mapped to +39.5 GB). Not seen in the 38 later runs; the cause is unknown.
- `virtual_pools sparse` is a profile key: whether every game's virtual pools can be sparse is not tested ([Small virtual pools made sparse](../../../docs/reference/nvn-objects.md#small-virtual-pools-made-sparse-virtual_pools-sparse)).
